# Maestroフローファイルルール

対象: `doc\03_結合テスト\maestro\*.yaml`、`doc\03_結合テスト\test-data\vars\*.json`

テスト仕様書の書き方は「テスト仕様書ルール」を参照してください。

## 1. 目的

テスト仕様書の 1 ケースを、実機の画面操作で確認できる形にします。フローは、仕様書の操作と期待値を、Maestro の書き方で再現します。

## 2. ファイルと構成

- ファイル名は `<節>-<通番>-<内容>.yaml` の形にします（例: `2.1-01-top-navigation.yaml`）。仕様書の通番と一致させます。
- 1 行目は、目的と対応するテスト仕様書の番号を書きます（例: `# 2.2 送信先の設定: 設定を追加と削除（テスト仕様書の 2.2 に対応）`）。
- 2 行目に `appId`、3 行目に `---` を書き、その後に手順を書きます。
  ```yaml
  # 2.2 送信先の設定: 設定を追加と削除（テスト仕様書の 2.2 に対応）
  appId: com.ssfrontier.smstokintone
  ---
  - launchApp:
      clearState: true
  ```
- 文字コードは UTF-8（BOM なし）、改行は CRLF、インデントは 2 つの空白で書きます。
- 1 つのフローには、1 つのテスト仕様書の通番だけを書きます。
- 値は、フローに直接書かず、変数（`${変数名}`）にして、後述の `test-data\vars` のファイルから渡します。

## 3. 操作の書き方

- 画面の文字で操作できる部品は、`tapOn: "文字"` で書きます。
- 同じ文字の部品が複数あるときは、`id` と `index` を書きます（例: `id: "com.ssfrontier.smstokintone:id/etSendTargetName"`、`index: 0`）。`id` は `com.ssfrontier.smstokintone:id/<ビューの id>` の形で書きます。
- 画面の下にある部品は、操作の前に `scrollUntilVisible`（`element`、`direction: DOWN`）で表示します。
- 入力は `inputText` で行います。入力の後は、`hideKeyboard` でキーボードを閉じてから次の操作をします。キーボードが部品を隠すと、次の操作が失敗します。
- 入力先に既存の値がある場合、`eraseText` はカーソルより前の文字しか消しません。タップした位置にカーソルが置かれるため、後ろの文字が残ります。既存の値を消すときは、この動作を確かめてから書きます。
- `pressKey` は、Maestro が受け付けるキー名だけを書きます（例: `Enter`、`Backspace`、`Back`）。受け付けないキー名（例: `Select All`、`End`）は、パースの段階で失敗します。
- `relativePoint` は使えません（この Maestro 2.12.0 では未知のプロパティになります）。
- ラジオボタンとチェックボックスは、項目の文字（`tapOn: "文字"`）で選びます。同じ文字が複数あるときは、`id` と `index` で指定します（未確認）。
- 複数行のテキスト欄（テキストエリア）は、`inputText` で入力します。改行は `inputText` に書かず、`pressKey: Enter` で入れます（未確認）。
- 複数行の欄は、入力が画面の外に出るため、入力の後に `assertVisible` で一部の文字を確認します（全部は見ません）（未確認）。
- 欄の既存の値を消す操作は、テキスト欄と同じく、カーソルの位置に注意します（3 章の  の項を参照）。
- 待ち時間は、`sleep` のような固定の待ちを入れず、`assertVisible` などの確認で Maestro に待たせます。
- 入力の文字は、日本語を含まない英数字にします。日本語入力のキーボード（12 キーなど）では、英数字が正しく入りません。実機の入力方式は、英語にしておきます。

## 4. 確認の書き方

- 操作のあとは、画面の期待値を `assertVisible`（表示される）または `assertNotVisible`（表示されない）で確認します。確認のない操作を続けて書きません。
- 入力した値は、`assertVisible: "${変数名}"` で、画面に表示されたことを確認します。
- 結果の画面は、`takeScreenshot` で残します。名前は `<フローの名前>` の後に内容を付けます（例: `2.2-01-after-add`、`2.2-01-after-delete`）。
- 1 つのフローの最後には、確認した結果の画面（スクリーンショット）を残します。

- ラジオボタン、チェックボックス（選択の確認）: 選んだ後に、その項目が選ばれていることを `assertVisible` の `checked: true`（または `selected: true`）で確認します（未確認）。選ばれていないことは `checked: false` で確認します。
- 複数行のテキスト欄: 入力した文字の一部（行の先頭など）を `assertVisible` で確認します（未確認）。

## 5. 値の渡し方

- フローは、`${変数名}` で値を参照します。変数名は英大文字と `_` で書きます（例: `SEND_TARGET_NAME`）。
- 値は `test-data\vars\<フローの名前>.json` に書きます（例: `2.2-01-send-target-add-delete.json`）。`run-tests.ps1` が、フローと同じ名前の JSON を読み込んで `-e` で渡します。
  ```json
  {
    "SEND_TARGET_NAME": "test-target-a"
  }
  ```
- 認証の値（ログイン名、パスワード、アプリ ID など）は、リポジトリに実際の値を書きません。`vars` のファイルは、プレースホルダーの値で作り、実際の値は手元で書き換えます。
- フローの `env:` に既定値を書く方法は使いません。値は `vars` の JSON に書きます。

## 6. フローの並び順と状態

- 実行は、ファイル名の順（`2.1`、`2.2`…）に行います。
- `launchApp` の `clearState: true` は、アプリのデータを消します。前のフローで入れた設定（送信先など）が消えるため、次のどちらかにします。
  - 前のフローの状態を引き継ぐフローでは `clearState` を書きません。
  - `clearState: true` のフローは、実行順の最後にします（例: `2.2` は `2.1` の後に実行します）。
- フローが前提にしている状態（送信先の設定など）は、フローの 1 行目の注釈に書きます。
- 1 回だけの準備（設定の入力など）は、フローとして作りません。手動で行い、その前提を、テスト仕様書の前提条件に書きます。

## 7. 注意

- 操作の順番と画面の名前は、画面設計（`doc\02_設計\画面設計.md`）と一致させます。画面、部品が変わったときは、フローも同じタイミングで更新します。
- 実機で確かめていない操作は書きません。書いた場合は、フローの 1 行目の注釈に「（未確認）」と書きます。
- フローの実行に失敗したときは、パースのエラー（書き方の誤り）と、画面の失敗（期待する文字がない）を区別して確認します。パースのエラーは、行番号を見て、キー名や YAML の書き方を直します。

## 8. 記述例

`doc\03_結合テスト\maestro\2.2-01-send-target-add-delete.yaml`（抜粋）

```yaml
# 2.2 送信先の設定: 設定を追加と削除（テスト仕様書の 2.2 に対応）
appId: com.ssfrontier.smstokintone
---
- launchApp:
    clearState: true
- tapOn: "送信先の設定"
- assertVisible: "設定を追加"
- tapOn: "設定を追加"
- assertVisible: "設定 2"
- tapOn:
    id: "com.ssfrontier.smstokintone:id/etSendTargetName"
    index: 0
- inputText: "${SEND_TARGET_NAME}"
- assertVisible: "${SEND_TARGET_NAME}"
- takeScreenshot: 2.2-01-after-add
```

- `clearState: true` のフローは、実行順の最後にします（6 章）。
- 入力した値は、`assertVisible` で画面に表示されたことを確認します（4 章）。
