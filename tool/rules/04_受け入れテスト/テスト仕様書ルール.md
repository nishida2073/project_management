# テスト仕様書ルール（受け入れテスト）

対象: `doc\04_受け入れテスト\テスト仕様書.md`

共通の書き方は「共通ルール」を参照してください。

## 1. 目的

利用者の業務の要件を満たすかを、業務の流れで確認します。画面ごとの細かい項目は、結合テストで確認済みとして、ここでは見ません。

## 2. 書く内容

- 文書は次の構成で書きます。
  - `## 1. 概要`: テストの対象、実施環境、事前条件を、箇条書きで書きます。
    - 実施環境は、テストを行う環境（kintone の環境など）だけを書きます。
    - 事前条件は、テストを始める前に用意しておく状態（テスト用のグループ、テスト用のファイルなど）を書きます。実施環境には書きません。
    - 事前条件は、すべてのテストケースに共通する前提だけを書きます。
    - 事前条件は、文章ではなく「項目：値」の形で、箇条書きにします（例: `テスト用のグループ：「ok」`）。値は「」で囲みます。
    - 用語の説明は、概要には書きません（`## 2. 用語` に書きます）。
  - `## 2. 用語`: テストで使う用語を表で書きます（用語、意味）。用語は、本書で使う業務の言い方を書きます。画面の項目名（「対象のグループ」など）や、具体的な値は書きません。
    - 用語は、本書の中で使うものだけを書きます。
    - 意味は、一文で書きます。
  - `## 3. 要件`: 要件の一覧を表で書きます（要件 ID、内容）。要件 ID は `R-01` の形にします。
    - 内容は、利用者が業務でできることを書きます。「〜できる」の形で書き、語尾をそろえます（例: `シートごとに分けたパッケージ（zip）を作成できる`）。
    - 機能の名前だけを書きません（例: 「テスト接続」「ログ」と書かず、「テスト接続で、kintone へ接続できるかを確認できる」のように、何ができるかを書きます）。
    - 「〜の確認や〜の削除」のように名詞を並べず、「〜を確認し、〜を削除できる」の形にします。
    - 内容には、具体的な値（グループ名、タイトルなど）を書きません。
    - 同じ意味の語は、同じ書き方にそろえます（例: 「kintone へ」と「kintone への」を混在させない）。
  - `## 4. テスト`: 要件ごとに節を分けます。見出しは要件 ID だけにします（例: `### 4.1 R-01`）。要件の文は書きません（`## 3. 要件` に書いてあります）。
    - 節の並びは、要件 ID の順に合わせます。
- 各要件の節では、次の順に書きます。
  1. `#### 合格条件`: その要件を満たしたと言える状態を、箇条書きで書きます。
  2. `#### テストケース`: 合格条件を確かめる手順を、表で書きます。
- 合格条件は、表の前に書きます。テストケースの表で確かめる内容を、先に読めるようにするためです。
- 表の列は次の 5 つです。
  - 通番: 表ごとに 1 から振ります（節ごとに振り直します）。
  - 事前条件: そのケースの前提です。概要の事前条件と同じ場合は「概要と同じ」と書きます。概要と違う前提がある場合だけ、その前提を書きます。
    - 前のケースの結果が必要な場合は、次の形で書きます。
      - 同じ節の前のケース: 「ケース N の後」（例: `ケース 1 の後`）
      - 別の節のケース: 「要件の節番号 の N 番の後」（例: `4.2 の 1 番の後`）
    - 状態の説明は、「（〜がある）」の形で、後ろに付けます（例: `4.2 の 1 番の後（ログがある）`）。
    - 状態の説明に出てくるファイル名や値は、「」で囲みます（例: `（既定の出力先に「コースA.zip」がある）`）。
    - 操作で元に戻す値（テスト中に変えた設定）は、そのケースか、後のケースで戻します。戻すケースの事前条件は、変えたケースを「ケース N の後」で書きます。
  - 操作: 利用者が業務の流れで行う操作です。ボタン名、タブ名、項目名は「」で囲みます（例: 「実行」を押します。）。入力する値や選ぶ値（グループ名、タイトルなど）も「」で囲みます（例: 対象のグループ「ok」を選び、タイトルに「テスト1」を入力します。）。「」の前後に空白は入れません。
  - 期待値: 操作の結果として、利用者が確認できる状態を書きます（画面の表示、状態、作られるファイルなど）。
  - 実施結果: テストを実施したときに記入する列です。文書では空欄にします。
- 列を増やさないものは、次のとおりです（書きません）。
  - 要件 ID（節の見出しで分かります）
  - 区分（正常系・異常系）
  - 参照（画面設計、処理フローの節）
  - 確認者、確認日
- 値は、列を作らず、操作の文の中で表します。結果を左右する値（グループ名、タイトルを空にする、など）だけを書きます。結果に関係ない値は省きます。
- 1 つのテストケースには、確認する 1 つの流れを書きます。
- 操作と期待値に出てくる名前（タブ名、ボタン名、項目名、表示される文言）は、画面設計と処理フローに書いた名前と同じにします。
- 期待値は、画面設計と処理フローに書いた内容から取ります。設計に書かれていない動作を期待値にする場合は、「（未確認）」と明記します。
- 各要件の節の最後（次の `###` 見出しの直前）に、次の行を書きます。ただし、次が章の見出し（`##`）の場合や、文書の最後の節の場合は、この行を書きません。

## 3. 注意

- テストの内容は、業務の要件に合わせて書きます。
- 画面の詳細（項目ごとの表示、入力の検査など）は、結合テストで確認します。受け入れテストでは、業務の流れが終わるかを確認します。
- 実行は番号順に行われるとは限りません。前の要件の結果を使うケースは、事前条件か注意事項に、どの結果を使うかを書きます。
- この文書は、結合テストの仕様書や画面設計、処理フローを変更したときに、必要に応じて更新します。
