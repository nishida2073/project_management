# テスト仕様書ルール（受け入れテスト）

対象: `doc\04_受け入れテスト\テスト仕様書.md`

共通の書き方は「共通ルール」を参照してください。

## 1. 目的

利用者が業務を遂行できるかを、業務の流れで確認します。画面の細かい項目や入力の検査は、結合テストで確認済みとして、ここでは見ません。

## 2. 書く内容

- 文書は次の構成で書きます。
  - `## 1. 概要`: テストの対象、実施環境、注意事項を、箇条書きで書きます。
    - 実施環境は、テストを行う環境（kintone の環境など）だけを書きます。
    - 注意事項は、「注意事項」の項目にまとめます（例: `- 注意事項` の下に `テスト中、ツールが使うファイルを別のアプリで開かない`）。
    - 用語の説明は、概要には書きません（`## 2. 用語` に書きます）。
  - `## 2. 用語`: テストで使う用語を表で書きます（用語、意味）。用語は、本書で使う業務の言い方を書きます。画面の項目名（「対象のグループ」など）や、具体的な値は書きません。
    - 用語は、本書の中で使うものだけを書きます。
    - 意味は、一文で書きます。
  - `## 3. 要件`: 要件の一覧を表で書きます（要件 ID、内容）。要件 ID は `R-01` の形にします。
    - 内容は、利用者が業務でできることを書きます。「〜できる」の形で書き、語尾をそろえます（例: `シートごとに分けたパッケージを作成できる`）。
    - 機能の名前だけを書きません（例: 「テスト接続」「ログ」と書かず、「テスト接続で、kintone へ接続できるかを確認できる」のように、何ができるかを書きます）。
    - 名詞を並べず、「〜を確認し、〜を削除できる」の形にします。
    - 内容には、具体的な値（グループ名、タイトルなど）を書きません。
    - 同じ意味の語は、同じ書き方にそろえます（例: 「kintone へ」と「kintone への」を混在させない）。
  - `## 4. テスト`: 要件ごとに節を分けます。見出しは要件 ID だけにします（例: `### 4.1 R-01`）。要件の文は書きません（`## 3. 要件` に書いてあります）。
    - 節の並びは、要件 ID の順に合わせます。
- 各要件の節では、次の順に書きます。
  1. `#### 利用資材`: テストで使う物（グループ、設定ファイル、フォルダ、ファイルなど）を、項目と値で書きます（下の「利用資材と事前条件の書き方」を参照）。表の「事前条件」の列とは別に書きます。
  2. `#### 合格基準`: 下の「合格基準の書き方」を参照。
  3. `#### テストケース`: 合格基準を確かめる手順を、表で書きます（下の「テストケースの選定」「期待値の書き方」を参照）。
  4. `#### テスト後の復元`: すべての節に書きます。表の後に置きます。テスト中に変えた設定を、元に戻す手順を箇条書きで書きます。戻すだけの手順は、テストケースの表には入れません。変えた設定がない場合は、`- 特になし。` と書きます。
- 合格基準は、表の前に書きます。テストケースの表で確かめる内容を、先に読めるようにするためです。
- 表の列は次の 5 つです。
  - 通番: 表ごとに 1 から振ります。
  - 事前条件: そのケースの前提です（下の「利用資材と事前条件の書き方」を参照）。
  - 操作: 利用者が業務の流れで行う操作です。ボタン名、タブ名、項目名は「」で囲みます（例: 「実行」を押します。）。入力する値や選ぶ値も「」で囲みます（例: 対象のグループ「test01」を選び、タイトルに「テスト1」を入力します。）。「」の前後に空白は入れません。
  - 期待値: 業務の結果として、利用者が確認できるものを書きます（下の「期待値の書き方」を参照）。
  - 実施結果: テストを実施したときに記入する列です。文書では空欄にします。
- 列を増やさないものは、次のとおりです（書きません）。
  - 要件 ID（節の見出しで分かります）
  - 区分（正常系・異常系）
  - 参照（画面設計、処理フローの節）
  - 確認者、確認日
- 1 つのテストケースには、確認する 1 つの流れを書きます。
- 操作と期待値に出てくる名前（タブ名、ボタン名、項目名、表示される文言）は、画面設計と処理フローに書いた名前と同じにします。
- 期待値は、画面設計と処理フローに書いた内容から取ります。設計に書かれていない動作を期待値にする場合は、「（未確認）」と明記します。
- 各要件の節の最後（次の `###` 見出しの直前）に、次の行を書きます。ただし、次が章の見出し（`##`）の場合や、文書の最後の節の場合は、この行を書きません。

  `<div class="pagebreak"></div>`

## 3. 利用資材と事前条件の書き方

- 利用資材は、その要件のテストケースに共通する前提を書きます。概要に書いた注意事項とは、重ねて書きません。
- 「項目：値」の形で、箇条書きにします。値は「」で囲みます（例: `グループ：「test01」`）。
- 「項目：値」の下に、詳細な説明の文を入れ子で書いてよいです（例: `グループの設定ファイル：「test01.bat」` の下に `kintone の接続情報と対象アプリIDが、テスト用の値で保存されている`）。
- 利用資材の「項目：値」は、テストケースの表の期待値（下の「期待値の書き方」）とは書き方が異なります。利用資材は箇条書きの入れ子で書き、期待値は表のセルの中で「、」で続けて書きます。
- 項目は、入れ子で書きます。グループの中にグループの設定ファイルとパッケージ定義ファイルを置き、設定の中身はさらに下に置きます。
  - 例:
    - `グループ：「test01」`
      - `グループの設定ファイル：「test01.bat」`
        - `サブドメイン、ログイン名、パスワード、対象アプリIDが、テスト用の値で保存されている`
      - `パッケージ定義ファイル：「test01.xlsx」`
        - `シート「コースA」と「コースB」を含む`
- 圧縮元のフォルダは、グループの設定ファイルの中の項目です（例: `圧縮元のフォルダ：「download」`）。
- 利用資材は、そのテストで必要なものだけを書きます。使わないグループ（接続情報を使わないログの確認など）の設定は書きません。
- 事前条件の欄（表の列）は、次のどれかを書きます。
  - 「利用資材と同じ」: ケースが節の利用資材だけで足りる場合。
  - 「操作：〜」: 前のケースや、ほかの節の操作の結果が必要な場合（例: `操作：ケース 1`、`操作：4.2 の 1 番`）。
  - 「操作：〜」に、ケースで必要な項目を続けて書く: 前の操作の結果に加えて、このケースで必要な設定がある場合（例: `操作：4.2 の 1 番、既定の出力先：「コースA.zip」`）。
- 前の操作の結果を使うときは、必ず「操作：」を付けて書きます。
- 同じ節の前のケースを使う場合は「操作：ケース N」、別の節のケースを使う場合は「操作：節番号 の N 番」と書きます。
- テスト中に変えた設定は、テスト後の復元で元に戻します。戻すための操作は、テストケースの表には入れません。

## 4. 合格基準の書き方

- 合格基準は、その要件を満たしたと言えることを、業務の結果で書きます。
- 1 つの要件に、合格基準は 1〜3 項目にします。1 項目には、結果を 1 つだけ書きます。ただし、一括実行のように 1 回の操作で複数の処理が行われる場合は、その結果をまとめて 1 項目に書いてよいです。
- 画面の項目名（タブ名、ボタン名、一覧、項目名など）と、画面の操作（押す、入力するなど）は書きません。「選ぶ」「選択する」「保存する」は、業務の言葉として使ってよいです。業務の言葉で書きます（例: `パッケージの作成とアップロードを両方行うと、パッケージが作られ、kintone にアップロードされる。`）。
- 合格基準は、「利用者は、」などの主語で始めません。結果を直接書きます。
- 画面の表示（ボタンの状態、一覧の並び、メッセージの細かい文言）だけを合格基準にしません。
- 結果が、ある時点での状態として確かめられる場合は、状態を表す言葉で書きます（例: `圧縮元のフォルダがない場合は、状態が警告になる。`、`不要になったログを削除すると、ログが残らない状態になる。`）。
- 状態として書けない結果は、そのとおりに書きます（例: `対象のシートを指定すると、そのシートだけが zip になる。`、`同じタイトルのレコードがあれば更新され、なければ作られる。`）。
- 条件は、「〜すると」「〜場合は」「〜があれば」で書きます。
- 文末は、「〜になる」「〜される」「〜できる」「〜作られる」などの結果の言葉で書きます。
- 合格基準で、テストケースの番号（「1 番」「ケース 2」など）は書きません。
- 合格基準は、表の前に書きます。

## 5. 期待値の書き方

- 期待値は、業務の結果として、利用者が確認できるものだけを書きます（作られるファイル、登録されるレコード、削除されたログ、表示される状態など）。
- 「項目：値」の形で書き、項目どうしは「、」で続けます（例: `状態：成功、パッケージ：「コースA.zip」`）。
- テストケースの表の期待値は、利用資材（「3. 利用資材と事前条件の書き方」）の入れ子の箇条書きとは書き方が異なります。期待値は、表のセルの中に 1 行で書きます。
- 期待値は、次のどちらかの形で書きます。
  - 基本: 「項目名：値」（値は、名詞や状態の名前で書きます。例: `状態：成功`）
  - 詳細版: 「項目名：値を詳細化する文」（値の部分を、文で詳しく書きます。例: `パッケージ定義ファイル：「test01.xlsx」の「テンプレート」シートが「download」の内容と同じ`）
- 値の中に「：」は使いません。
- 状態は、状態の名前を付けて書きます（例: `状態（パッケージの作成）：警告`）。
- パッケージは「パッケージ：「コースA.zip」」の形で書きます（zip の名前は、シート名に「.zip」を付けたものです）。
- kintone のレコードは「kintoneのレコード：「テスト1」（「コースA.zip」が添付される）」の形で書きます。
- 作られなかったものは「〜は作られない」「〜のみ」のように書きます。
- 期待値に入れるファイルや値は、「」で囲みます。
- 期待値の状態（成功、警告など）は、業務の結果を確かめるために必要な場合だけ書きます。すべてのケースに状態を書く必要はありません。

## 6. テストケースの選定

- 業務を遂行することを中心に選びます。画面の操作の確認は、ケースの中心にしません。
- 要件ごとに、テストケースは合格基準を確かめるのに必要な数だけ書きます（目安は 2〜4 件）。
- 次のケースを選びます。
  - 業務の正しい流れ（例: 一括実行で、パッケージの作成とアップロードを行う）
  - 業務上の分岐（例: 一部が警告になっても、後続の処理が続けて行われる）
  - 業務の結果が変わる設定（例: 対象のシートを指定すると、そのシートだけが zip になる）
- 次のケースは、選びません（結合テストで確認済みとします）。
  - UI が原因の入力エラー（空欄、未入力のメッセージなど）
  - 画面の表示だけを確かめるもの（ボタンの状態、タブの切り替え、「開く」のリンクなど）
  - 画面上の細かい操作（ラジオボタンの切り替え、コンボボックスの選び直し、「再読込」など）
  - キャンセル（「いいえ」で閉じるなど）、重複の入力など、画面の細かい分岐
- 戻すだけの操作（設定を元に戻す）は、テストケースにしません。テスト後の復元に書きます。

## 7. 注意

- テストの内容は、業務の要件に合わせて書きます。
- 画面の詳細（項目ごとの表示、入力の検査など）は、結合テストで確認します。受け入れテストでは、業務の流れが終わるかを確認します。
- 実行は番号順に行われるとは限りません。前の要件の結果を使うケースは、事前条件に「操作：」で、どの結果を使うかを書きます。
- この文書は、結合テストの仕様書や画面設計、処理フローを変更したときに、必要に応じて更新します。
